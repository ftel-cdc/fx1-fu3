# GT32U2086 build and boot contract

The target name, device macro and build preset are `GT32U2086`. All GT32U2086 applications
use the RTL BootROM v5 image contract from Test_VP; there is no separate ROM
variant or legacy raw-slot build. Peripheral addresses follow GT32U2086's current
register map. ROM revision and MCU register-map revision are separate concepts.
The Cortex-M0 core supports up to 60 MHz. A fixed FPGA clock setting describes
the clock actually supplied by the board, rather than the maximum CPU rating.

| Resource | Normal Flash | QSPI XIP |
|---|---|---|
| Complete boot image base | `0x00020000` | `0x30000000` |
| Header size | `0x80` | `0x80` |
| Application vector base | `0x00020080` | `0x30000080` |
| Payload capacity | `0x7FF80` | `0x3FF80` |
| Application RAM | `0x01001000`–`0x0101FFFF` | Same |
| Initial stack top | `0x01020000` | Same |

Physical Flash/RAM definitions remain unchanged in `GT32U2086.yaml`; its normal/XIP
profiles reserve the image header and the first 4 KB of SRAM. The first two SRAM
words hold the ROM-published vector base and exclusive payload end. Startup
copies only application `.data` and clears only application `.bss`, preserving
those words. Cortex-M0 has no VTOR: interrupt forwarding is provided by the ROM.

BootROM v5 hands over with `PRIMASK=1`, all NVIC sources disabled and pending
interrupts cleared. An application using interrupts must call `__enable_irq()`
after its runtime and interrupt sources are ready; `NVIC_EnableIRQ()` alone
does not clear the global mask. Peripheral drivers preserve PRIMASK across
their critical sections.

## Build

For Test_VP or a Neon application such as Blinky:

```sh
cmake --preset GT32U2086 --fresh
cmake --build --preset GT32U2086
```

The linker script is generated inside each build directory from the selected `GT32U2086.yaml` profile.
`neon_mdf_add_executable()` packages the ROM image
automatically. Standalone examples call `neon_mdf_add_gt32u2086_image()` from
`neon-mdf/cmake/gt32u2086_image.cmake` after generating the GT32U2086 device files.

Outputs:

| File | Profile `normal` | Profile `xip` |
|---|---|---|
| Raw vector/code/data payload | `<app>.bin` | `<app>_xip.bin` |
| Header plus payload for ROM boot | `<app>_image.bin` | `<app>_image_xip.bin` |

An ELF suffix, when configured by the project, also appears in the raw payload
filename, before `_xip` when present. ELF and target names keep their existing names.
The default app version is `0.0.1`; set `-DNEON_MDF_GT32U2086_APP_VERSION=1.2.3` to change
it. Builds produce non-secure images with header and payload CRCs. Signing and
NVR generation are available through the shared tool:

```sh
python3 neon-mdf/tools/gt32u2086_image.py info /path/to/app_image.bin
python3 neon-mdf/tools/gt32u2086_image.py nvr --secure-mode 0 -o /path/to/nvr.bin
python3 neon-mdf/tools/gt32u2086_image.py image --input /path/to/app.bin \
  --elf /path/to/app --flash-addr 0x20000 --key /path/to/key.pem \
  --output /path/to/app_image.bin
```

Non-secure packing uses Python's standard library; signing needs `cryptography`.
Image packing checks the ELF vector location, SRAM placement, stack, reset
address and Flash capacity, rejecting stale raw-image layouts.

## XIP

Keep the target/preset name `GT32U2086` and select the memory profile:

```sh
cmake --preset GT32U2086 --fresh -DNEON_MDF_PROFILE=xip
cmake --build --preset GT32U2086
```

Project helpers keep generated device files under each build directory.
For concurrent normal/XIP builds, use a separate directory such as
`cmake --preset GT32U2086 -B build/GT32U2086-xip -DNEON_MDF_PROFILE=xip`,
then `cmake --build build/GT32U2086-xip`. An image header's Flash base must match its linked
payload. QSPI-copy boot uses an internal-Flash-linked image; it is distinct from
an XIP image linked at `0x30000080`.

## UART programming

GT32U2086 Flash Tool 1.0 is integrated with the image-packaging helper. Configure
without serial settings, then pass the port and ROMCODE baud at execution time:

```sh
cmake --preset GT32U2086
cmake -E env NEON_MDF_SERIAL_PORT=/dev/ttyUSB0 NEON_MDF_SERIAL_BAUD=19200 \
  cmake --build --preset GT32U2086 --target flash_uart_gt32u2086
```

Select hardware boot mode `100`, wait for `[WAIT] UART is ready`, then press
RESET. This target programs the normal image into Internal Flash. XIP images
are rejected before UART is opened. See [flash firmware GT32U2086 via UART](GT32U2086Flashing.md)
for boot modes, runtime parameters, monitoring and troubleshooting.
For per-mode firmware preparation and boot procedures, see
[GT32U2086 boot modes and firmware workflow](GT32U2086BootModes.md).

## Runtime and peripherals

GT32U2086 application SRAM data accesses are aligned 32-bit transactions. The SDK
propagates the compiler policy and supplies word-access memory helpers.
The GT32U2086 FreeRTOS port widens internal byte flags/locks and uses aligned-word
access for task names and SVC decoding; static object layouts follow the same
ABI. Rebuild all objects when changing targets. Custom sources and third-party
libraries must obey the same bus contract.

Include `<string.h>` to use the GT32U2086 runtime implementations of `memcpy`,
`memmove`, `memset`, `memcmp`, `memchr`, `strlen`, `strcmp`, `strncmp`,
`strcpy`, `strncpy`, `strcat`, `strncat`, `strchr`, `strrchr`, `strstr`,
`strspn`, `strcspn` and `strpbrk`. Standard GT32U2086 project helpers link these
implementations automatically; they access bytes through aligned 32-bit words.
Each buffer/string must own the complete aligned words containing its bytes,
including its terminator. For example, use `uint32_t storage[16]` as a 64-byte
buffer and pass `(char *)storage`. Destination capacity and C string rules
still apply: `strncpy` pads to its count and may omit the terminator when
truncated; `strncat` needs space for the existing string, appended bytes and
terminator. These functions do not support MMIO or concurrently modified DMA
buffers, and do not change direct byte/halfword accesses in application code.

Drivers, console, applications and the FreeRTOS port use these standard
`<string.h>` functions for normal-memory buffers. Their implementations are
linked from `gt32u2086_runtime.c`; only that file uses `neon_utils_memory.h` as its internal
backend. Peripheral registers still use explicit
volatile word accesses: read a register into a `uint32_t` local, then use
`memcpy` to publish its bytes to a RAM buffer. Do not pass MMIO addresses
directly to the memory/string functions.

GT32U2086 builds `printf` and its `_write` output hook when
`CONFIG_NEON_MDF_DRIVER_UART=y`; no separate printf feature flag is needed.
Disabling UART removes both the UART backend and console from the build.
Include `<stdio.h>` and call `printf`: the `_write` output hook initializes
UART0 at 19200 baud, 8N1 on first output, using `SystemCoreClock`. Attaching an
initialized UART through `neon_console_attach_uart()` is optional when a different
UART/baud is needed. The word-only formatter supports strings and integer/hex
formats, including 64-bit integers; floating point and full newlib stdio are
not supported. See [PrintfLogging.md](PrintfLogging.md) and
[Printf_Log](../examples/Printf_Log/README.md). Standard GT32U2086 project helpers
select the SDK's word-only CLZ runtime before libgcc, including when normal
clock calculations require 64-bit division.

UART polling follows `dti_usart_ctrl_ug_rev1p3`: TX waits for LSR[5] THRF=0
before each THR write and returns when all bytes are queued, without waiting
for LSR[6] TEMT. Wait for TEMT separately before reset, baud changes or pin
changes; otherwise queued output can be lost. RX waits for LSR[0] DR=1.
Use `neon_uart_wait_tx_complete()` to wait for TEMT with a bounded polling
budget before reconfiguration. `neon_uart_try_receive()` reads one available
element into a complete aligned `uint32_t` without waiting, returns TIMEOUT
when empty, and may run in the UART ISR while polling TX is BUSY_TX. It keeps
the interrupted TX state intact. Use only one RX consumer and serialize
configuration/teardown; do not call polling receive concurrently with ISR RX.
FCR[0] is active-low: 0 enables FIFOs, 1 selects non-FIFO mode and clears
their counters. ClearRxFIFO/ClearTxFIFO require FIFO mode. This revision
does not define RX threshold bits, so GT32U2086 accepts only the default
`fifo_threshold` value and returns NOT_SUPPORTED for other selections.

IIR pending is active-high. IDs are 0=none, 1=TX full, 2=RX ready, 3=line
error, 4=character timeout, 5=DMA TX done and 6=DMA RX done. The old TX_READY
names are compatibility aliases for TX_FULL on GT32U2086. RX_TIMEOUT now has ID 4;
MODEM is a reserved logical ID outside the GT32U2086 hardware ID range. Rebuild
applications using the updated header. `NEON_UART_INTERRUPT_ALL` selects
sources only; AUTO_CLEAR and MANUAL_CLEAR select clearing policy separately.
enable AUTO_CLEAR clears IER[4]; enable MANUAL_CLEAR sets it. In manual mode,
read IIR once through GetInterruptID and check NONE, because reading IIR also
acknowledges the event. A separate IsInterruptPending call can consume it.

CLKS[0] is the clock-fault flag, [12:1] contains the failed APB address and
[13] the command (0=write, 1=read). The driver caches a fault in
`handle.clock_status` before the hardware clears CLKS on read; only the flag
sets `NEON_UART_ERROR_CLOCK`. The remaining fields are diagnostic metadata.
Nine-bit TX selects LCR_EXT[3]=1 so THR accepts the ninth data bit. Five-bit
data with the public two-stop-bit setting is rejected because this hardware
combination actually produces 1.5 stop bits. parity follows Table 14 of the
guide; the EPS prose in Table 13 contradicts that table and needs RTL/hardware
confirmation before changing parity polarity.

ADC and DMA APIs now describe the current hardware rather than the older IPs:

- ADC init uses `channel`, `sample_source`, `sample_count`, `sample_clock_low`,
  `sample_clock_high` and `setup_wait`; call `neon_adc_get_default_config()` first.
  `neon_adc_read_samples()` returns 12-bit samples in a `uint16_t` buffer owning
  its complete aligned words. It reads sample slots, not a byte FIFO.
- DMA uses native FTEL channel command registers. Config fields include
  `transfer_size`, `read_config`, `write_config`, `control` and `peripheral_config`.
  `StartChannel()` takes instance/config; `FireChannel()` takes instance/channel;
  `MemCpy()` takes instance/channel/destination/source/byte count/timeout. PL330 program
  buffers and debug instructions are removed. GT32U2086 requires aligned source and
  destination addresses, word-sized bursts and a byte count divisible by four,
  at most 1020 bytes per call. DMA timeout zero explicitly waits indefinitely.
- AES keeps the logical ECB/CBC/CTR API and uses native key/IV/input/output banks
  with READY/DONE polling. Serialize the singleton engine between tasks.
- The old OTP/eFuse driver is unavailable in the current memory map and is
  kept under `components/driver/efuse`, disabled in builds.
  ROM security records use Flash NVR via the Flash driver.

`neon_adc_read_samples()` and `neon_crc_calculate()` now take a final timeout
argument: a total poll budget, not milliseconds. Zero only checks readiness;
a timeout stops the ADC/CRC engine. `neon_dma_memcpy()` also takes a final poll
budget; a DMA wait timeout does not abort a channel already running.

SPI0 and SPI1 follow **DTI SPI User Guide rev1.1, chapter 9**. Offsets are:

| Register | Offset | Register | Offset |
|---|---:|---|---:|
| TX | `0x00` | CTRL | `0x04` |
| CONFCMD | `0x08` | DLR | `0x0C` |
| AR | `0x10` | ABR | `0x14` |
| FIFO | `0x18` | CLK | `0x1C` |
| CMDCONF | `0x20` | TREG0 | `0x24` |
| TREG1 | `0x28` | TREG2 | `0x2C` |
| RX | `0x30` | CLKS | `0x34` |
| STT | `0x38` | STT_DMA | `0x3C` |
| CTRL_RX | `0x40` | CTRL_TX | `0x44` |

CTRL uses SPI_MODE `[1:0]` (0=legacy slave, 1=legacy master, 2=extended DDR),
CPOL `[2]`, CPHA `[3]`, LSB `[4]`, INT_EN `[5]`, SS_MODE `[6]`, SS_FORCE `[7]`,
SS_LONG `[8]` and DMA_ENABLE `[9]`. Legacy master mode 3/MSB/polling is `0x0D`.
The old one-bit `SPI_CTRL_MA_EN` definition is replaced by `SPI_CTRL_SPI_MODE`.
Regenerate headers/SVD from GT32U2086.yaml and rebuild all affected objects.

Rev1.1 has conflicting legacy text: Table 4 lists RX at `0x1C`, while
section 4.3, Table 7 and section 9.14 consistently specify `0x30`. Section
7.1 mentions FIFO at `0x08`; sections 4.1/9.8 and Table 7 specify `0x18`.
One paragraph in 7.1 reverses TRAN_DONE polarity; Table 21 in 9.17 and the
subsequent rearm sequence use 1=complete. The HAL follows these register
descriptions and the consistent master/rearm sequences.

The SPI polling APIs implement legacy 8/16/24/32-bit master and 8-bit slave.
`neon_spi_set_data_width()` changes frame width while idle without resetting
the controller, preserving manual SS hold for header/payload sequences.
Extended DDR and circular-DMA registers are defined for inspection/raw use;
these modes are not implemented by the legacy transfer APIs.

GT32U2086 defaults to a pause of 10 complete SCK periods between data bytes,
including bytes within a 16/24/32-bit word. The default is defined by
`NEON_SPI_GT32U2086_B2B_SCK_CYCLES` under `#ifdef GT32U2086` in `spi/neon_spi.h`.
`timing.between_frames_unit=NEON_SPI_B2B_SCK_CYCLES` converts
`between_frames * 2 * (divider + 1)` to core-clock cycles in `TREG1.T_B2B`.
`neon_spi_set_clock_divider()` preserves the requested number of SCK
periods. Use `NEON_SPI_B2B_CORE_CYCLES` to program a raw core-cycle delay;
zero disables the byte pause. Initialization, timing changes and divider
changes reject values that cannot fit the 16-bit register before modifying
hardware. Rebuild all objects after the timing-structure change.

The `SPI_W5500` menu key `b` performs a read-only 10..0 SCK-period sweep.
It validates a 32-byte TX SRAM CRC32 reference at 10 periods, then compares
repeated reads against that fixed reference and checks VERSIONR=0x04.
It reports CRC/ID/transport errors and the smallest zero-error setting in
that run, restores the original SPI settings and leaves auto ping/pong off.
The sample count is `CONFIG_SPI_W5500_B2B_TRIES` (default 1000 per level).
This checks repeatability of inactive TX SRAM, not correctness against a
known written pattern; the reported minimum is specific to mode, speed and
sample count. An unstable reference or cancelled run reports no minimum.

There is no shifter-BUSY bit in rev1.1. After FIFO completion, master polling
adds a conservative core-cycle guard for the final serial clocks and applicable
SS setup/hold/timeout/inter-byte timing. It uses the existing polling budget,
assumes CPU and SPI core share the GT32U2086 system clock, and does not take over
SysTick or mask interrupts. Manual HOLD intentionally keeps CS asserted.
A polling timeout blocks further transfers/configuration until Init or DeInit
resets the controller, so a partial frame cannot silently contaminate a retry.

SPI DMA configuration is one-shot: program a disabled channel, pulse its CLEAR
bit `[21]`, then arm it. Reconfiguration requires the previous enabled channel
to report TRAN_DONE. Each direction is cleared separately; arming the other
direction for full duplex remains supported. Disable accepts a config with
only `state=DISABLE`. SS_FORCE alone can change during active DMA, as allowed
by section 4.4; SS_MODE/SS_LONG and other settings require idle hardware.
The application still configures DMAC and the DMA handshake/channel selection.

### Automatic pin configuration

GT32U2086 UART, I2C, SPI, QSPI and PWM initialize their SYSCSR pad/mux routes by
default. GPIO already configures its own GPIO mux and supported pad properties.
Applications do not need to write SYSCSR in a peripheral example.

| Driver | Default package pins |
|---|---|
| UART0 | TX=50, RX=51 |
| UART1 | TX=58, RX=59 |
| UART2 | TX=12, RX=13; JTAG mux is released/restored automatically |
| UART3 | TX=24, RX=25 |
| UART4 | TX=26, RX=48 |
| I2C0 | SDA=18, SCL=19 |
| SPI0 | SCK=60, MISO=61, MOSI=62, SS0=63 |
| SPI1 | SCK=20, MISO=21, MOSI=22, SS0=23 |
| QSPI | SCK=68, SSN=72, D0=71, D1=70, D2=69, D3=64 |
| PWM0/PWM1 | 73/74 |
| PWM on TIM0 | PWM_T0=48 (PB6) |

The serial/PWM backends share a SYSCSR helper that configures input feedback,
high drive, open-source off, and push-pull (UART/SPI/QSPI/PWM) or open-drain
(I2C). It supports all 24 pad indexes per side; pull and slew settings are kept.
I2C requires external bus pull-ups. Mux and pad bits are saved on the first
initialization and restored by DeInit. Reinitializing an active route keeps
the original snapshot; unrelated pins and later changes to their bits survive.
PWM AUTO routes channel 0; channel 1 requires KEEP because no package route
is defined for it. Deinitializing a KEEP channel leaves the AUTO route intact.
Drivers sharing a physical pin must be used sequentially.

Use each driver's `NEON_<driver>_PIN_CONFIG_KEEP` option when the board already
manages pin setup; AUTO is the zero/default value. Deinitialize an AUTO route
before handing its pins to board code or another driver. SPI masters with
`SLAVE_SELECT_NONE` configure only SCK/MISO/MOSI, leaving external GPIO CS
alone. Slave mode also configures SS0. SS1..3 have no package mapping and
return `NEON_NOT_MAPPED` in AUTO; KEEP allows board-managed routing.
UART RTS/CTS also requires KEEP because no default package mapping is defined.

Call `neon_*_get_default_config()` or zero-initialize configuration structs;
QSPI now also provides `neon_qspi_get_default_config()`. SPI/PWM/QSPI configs
have a new `pin_config` field: rebuild all users of these headers. Timer APIs
used only as internal counters and other APIs without a mapped pin function
do not change SYSCSR pin routing.

UART enforces one initialized handle per instance. DeInit releases ownership;
initialization failures release it too. RTC years use all four BCD digits
(1..9999), with calendar validation in SetDate.

QSPI supports SDR mode 0/3, Single/Dual/Quad phases, 1..4-byte addresses,
alternate bytes and memory-mapped reads. Zero-initialize command structures;
zero address size retains the three-byte default. Rebuild all users after
the configuration and command structure changes.

For an indirect transfer, call `neon_qspi_send_command()`, then pump the FIFO
with `neon_qspi_transmit_words()` or `neon_qspi_receive_words()`, then call
`neon_qspi_wait_complete()`. Buffers contain aligned packed words, low serial
byte first, and must have room for `ceil(data_length / 4)` words. The driver
converts logical byte counts to `DLR = data_length - 1`, checks FIFO full/empty,
and requires TC plus an idle controller before reporting completion. Legacy
`neon_qspi_wait_ready()` also finishes a pending command; the hardware BUSY
bit alone does not prove completion. After a timeout, abort before starting
another command. A failed partial buffer transfer leaves data pending; abort
it rather than restarting the same buffer from its first word.

For example, read a three-byte JEDEC ID after successful initialization:

```c
neon_qspi_command_t command = {
    .instruction = 0x9FU,
    .instruction_lines = NEON_QSPI_LINES_1,
    .data_lines = NEON_QSPI_LINES_1,
    .data_length = 3U,
    .receive_enable = 1U,
};
uint32_t id = 0U; /* Wire bytes occupy bits 7:0, 15:8 and 23:16. */
neon_status_t status = neon_qspi_send_command(QSPI_APB, &command);
if (status == NEON_OK) {
    status = neon_qspi_receive_words(QSPI_APB, &id, 100000U);
}
if (status == NEON_OK) {
    status = neon_qspi_wait_complete(QSPI_APB, 100000U);
}
```

Command-only frames temporarily use at least divider /32 and observe their
start before returning, even without TC. The start wait is bounded by
`NEON_QSPI_COMMAND_START_TIMEOUT_POLLS`. Successful completion or abort restores the
selected divider. Controller completion does not indicate the end of a NOR
erase/program cycle: the application must still read the chip's status/WIP.

Configure the NOR protocol/QE first, then use
`neon_qspi_enable_memory_mapped()` and read aligned words from the QSPI_XIP
window. `neon_qspi_abort()` flushes FIFOs and returns to indirect mode before
reconfiguration or DeInit. The code, constants, and other bus masters must
not access QSPI memory while changing/aborting its configuration. Automatic
status-polling, DDR and DMA transfers are not implemented by these APIs.

On the current FPGA backend TIM status is read-only live event state:
`STT_CH0` is at offset `0x4C`, `STT_CH1` at `0x50`. Reading flags does not
clear them or acknowledge an IRQ. UPDATE drops when the counter leaves the
reload condition. `neon_tim_clear_flag()` and `neon_pwm_clear_flags()` return
`NEON_NOT_SUPPORTED`; do not write STT. The periodic example bounds its wait
for UPDATE to drop and disables its IRQ on expiry. Measure event duration and
IRQ behavior on the actual bitstream. PWM shares this register contract.

The optional WDT driver provides config/DeInit/Refresh, counter reads and
interrupt acknowledgment. config enables its CRM clock and starts the watchdog;
timeout_range is the raw TOP value, so choose it for the board's watchdog clock.

ADC/AES/DMA/CRC/RTC/TRNG require CRM clock/reset setup before access.
GPIO has ClockEnable; UART/I2C/SPI/QSPI/TIM/PWM/WDT manage their own clocks at config.
The Test_VP 10-MHz fixed FPGA clock remains specific to that example. ROM v5
compatibility does not change silicon clock configuration or assume every board
uses the same oscillator.

The optional `gt32u2086_bootrom` target builds the vendored RTL ROM sources; see
`neon-mdf/components/bootrom/README.md`. Deploy applications against the chip's
ROM or the reference VP runner's pinned ROM and corresponding NVR policy.
